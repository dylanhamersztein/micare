# Practitioner sessions: Supabase issues the magic link, MiCare holds its own session

Practitioner sign-in uses Supabase Auth magic-links, but MiCare does **not** persist Supabase's access/refresh tokens or rely on Supabase RLS. Supabase Auth is used only to prove ownership of an email address: it sends the one-time link and verifies the token. Once an email is verified, the server mints MiCare's own sealed session cookie (`micare_session`, sealed by h3 via TanStack Start's `useSession`) carrying `{ practitionerId, email }`, and every subsequent request resolves the Practitioner by matching that email against `practitioners.email` over the existing service-role `pg` connection. This keeps the entire data layer on one path (service-role `pg`, which bypasses the deny-all RLS perimeter of ADR-0015), matches the `*_MOCK` flag pattern used for every other external dependency (`AUTH_MOCK` short-circuits the email send and signs a local dev token), and means local/CI runs need no GoTrue container. Trade-off: MiCare owns session lifetime/rotation itself rather than delegating to Supabase; acceptable because the session carries no authority beyond "this visitor owns this Practitioner's email", and all authorization is re-derived from the `pg` row on each request.
