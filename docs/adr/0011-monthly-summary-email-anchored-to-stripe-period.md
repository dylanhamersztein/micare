# The monthly summary email is anchored to Stripe's period bounds and deduped by a per-renewal ledger

The per-Practitioner monthly summary (issue #15, story 34) is a third Vercel Cron route — `/api/cron/monthly-summary`, daily at `0 9 * * *`, guarded by the same `CRON_SECRET` bearer check as the other two jobs (ADR-0007). Each run selects Practitioners with a live subscription (`active`, `trialing`, `past_due` — the set that will actually attempt a renewal, matching the consumer-visible set in ADR-0004), asks Stripe for the period each one is currently inside, and emails the ones whose period ends **on the next UTC calendar day**.

The billing period comes from **Stripe, not from local arithmetic**. Stripe is the system of record for subscription state (ADR-0010), and `practitioners.created_at` — what the dashboard's `currentBillingCycle` math uses — is only a proxy for the anchor: it drifts the moment a subscription is paused, resumed, or has its anchor moved. An email that quotes the wrong window on the day someone decides whether to keep paying is worse than one API call per Practitioner per day. Note that from API version `2024-11-20` Stripe moved `current_period_start` / `current_period_end` off the subscription and onto its **items**; MiCare pins `2026-04-22.dahlia`, so `src/server/billing-period.ts` reads `subscription.items.data[0]`, which is unambiguous while Phase 1 sells exactly one £29 price. Under `VITE_STRIPE_MOCK` there is no subscription to read, so the period falls back to the local `created_at` math — the same `*_MOCK` idiom as everywhere else, and what keeps the suite and local dev offline.

Idempotency uses a `public.monthly_summaries` ledger keyed `(practitioner_id, period_end)`, written **before** the send (record-first, as in ADR-0008). Keying on the renewal instant rather than the Practitioner is what makes the job safely re-runnable *and* still able to send next month: a replay for the same renewal conflicts and sends nothing, while the next cycle is a distinct key. The row also stores the `clickthrough_count` that was quoted, so an operator can answer "what did that email actually say?" without recomputing it against rows that have since moved. Counting itself is half-open `[start, end)` via `countClickthroughs`, now shared with the dashboard so the two readouts cannot drift in their window arithmetic.

Trade-offs accepted. **One Stripe call per eligible Practitioner per day** is fine at Phase 1 volume; the scale-up path is `subscriptions.list` filtered by a `current_period_end` range, which returns only the day's renewals in one paginated call. **A failed daily run silently skips that day's summaries** — there is no catch-up sweep, because widening the window to "renews within two days" would send the mail two days early on every healthy run; the issue explicitly treats a missed summary as non-catastrophic. **The dashboard still derives its cycle from `created_at`**, so for a Practitioner whose Stripe anchor has moved, the dashboard's window and the email's window can disagree; converging the dashboard onto `currentBillingPeriod` costs a Stripe call per dashboard render and was left out of this slice. **Vercel's Hobby plan caps cron jobs at two** — this is the third, so the deployed project needs Pro.
