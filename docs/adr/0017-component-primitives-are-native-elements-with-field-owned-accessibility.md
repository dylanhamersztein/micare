# Component primitives are native elements, and the Field owns the accessibility wiring

The shared presentational components live in `src/components/`, reached as `#/components`. There are eight of them — `Button`, `Field`, `TextInput`, `Textarea`, `Select`, `SegmentedRadio`, `VerificationBadge` and `Alert` — and every one is a thin wrapper over the native HTML element it stands for. No component library is installed, and none is planned for Phase 1.

**Native elements, because the behaviour we would be reimplementing is the behaviour we most need to get right.** MiCare's consumers skew towards people with impaired vision, and its practitioners skew towards people filling in a form once, on a phone, under mild duress. A native `<select>` opens with the platform's own picker; a native radio answers to the arrow keys without a `roving-tabindex` implementation; a native `<button>` fires on Space and Enter and announces its disabled state without an `aria-disabled` prop that someone will forget to pass. A headless library would hand back the same elements wrapped in a few hundred kilobytes of state machine, and a styled library would hand back its own design system to fight with the one in `src/styles.css` (ADR-0016). The components here exist to stop the same markup being retyped in five screens, not to replace what the browser already does.

**`Field` owns the wiring, and the control reads it.** Before this slice, every screen wrote its own label, its own help paragraph and its own `aria-describedby`, which is why the signup form, the search form, the Notify-Me form and the profile editor had four different answers to what happens to help text when an error appears. `Field` now generates the ids, decides the description chain, and publishes them on a React context that `TextInput`, `Textarea` and `Select` read; a caller writes `<Field label="…" help="…" error={error}><TextInput name="…" /></Field>` and cannot mis-wire it, because there is nothing left to wire. The error is added beneath the help text rather than replacing it, and the chain is ordered help-then-error, so a screen reader hears what the field wants before it hears what went wrong. Each control still accepts an explicit `id` and `aria-describedby` for use outside a `Field`, which is what keeps the primitive usable in the one-off cases without a second component for them.

**Nothing conveys its state through colour alone.** Each of the four Verification Statuses gets its own glyph and its own sentence, and each of the four alert tones does the same; the selected segment of the radius control carries a tick as well as a fill. The tests assert this as a property rather than a set of examples — that the four badges render four distinct glyphs, that each status puts its own words on the plaque — which is the form that survives someone adding a fifth state.

**A label must never name a date the badge does not hold.** `VerificationBadge` composes its `aria-label` from the same values it renders, so the no-date variant — the one that stands in for a record imported before checks began — reads "Checked weekly against the register" in both the visible line and the label. The alternative, an `aria-label` written once for the common case, is the bug this slice was written to avoid: a screen reader announcing a check date that no sighted user can see and that MiCare does not actually have. A test asserts the invariant directly in both directions, for every status and both variants: the badge names a date exactly when it was given one.

**The focus ring belongs to the segment, not to the radio inside it.** `SegmentedRadio` keeps a real, focusable radio in each segment and hides it visually with `position: absolute`. An absolutely positioned element resolves against the nearest positioned ancestor, so without one the ring drawn around the focused radio lands against the page rather than against the segment the user is on — the bug carried by the design's own specimen. Each segment is therefore `relative`, takes the ring itself through `has-[:focus-visible]`, and insets it, because the segments are butted together and an outset ring would be clipped by its neighbour.

**The tests compile the stylesheet rather than reading the class attribute.** A test that asserts `className` contains `bg-primary` passes when the token has been deleted. `tests/unit/support/rendered-styles.ts` takes a rendered element, runs `src/styles.css` through Tailwind's own compiler asking for exactly the classes that element carries, and resolves the resulting declarations through their `var()` indirection — so the assertions read "this button paints `#0d4a45`", "this segment is at least 44px tall", "this input's border turns `#96301c` when the field is invalid". This is the same technique ADR-0016 chose for the tokens themselves, extended from the stylesheet to the components that consume it, and it is what lets the 44px touch floor and the focus treatment be acceptance criteria rather than review comments.

**jsdom is opted into per file, not switched on for the unit project.** The unit suite is mostly pure functions, several of which resolve fixture paths through `import.meta.url`; jsdom rewrites that resolution and breaks them. Component tests therefore carry a `// @vitest-environment jsdom` docblock, and `tests/unit/setup.ts` registers React Testing Library's unmount only where a document exists. The alternative — a fourth vitest project — would have split the unit suite across two commands for no gain.

**"Badge" names the component, not the status.** `CONTEXT.md` warns against calling a Verification Status a "badge", and that still holds: the status is `verified`, `pending`, `rejected` or `revoked`, and the badge is the object that displays it. `VerificationBadge` is a UI element in the design's vocabulary, and naming it after what it draws keeps the domain term free for the thing the domain actually models.
