# Visibility is computed from the row, never stored on it

`practitioners.visible` was a Slice 1 stand-in for state machines that did not exist yet, and it has been dropped (migration `0009`). Whether a Practitioner is visible is now answered in exactly one place — `isVisible()` in `src/visibility.ts`, applied to `verification_status`, `subscription_status` and the minimum profile fields — by every caller, including the two maintenance crons that used to read the stored flag.

**The column could not be kept true, and being wrong was worse than being absent.** Only two writers maintained it (the profile save and the revocation branch of the weekly cron) while three paths changed the state it was derived from: the Stripe webhook, manual re-verification, and the profile save itself. The real Stripe sequence exposed the gap. A Practitioner's row starts at `subscription_status = 'incomplete'`; if they save their profile before Checkout completes, `visible = false` is written; the webhook then flips them to `active` without touching the column. Every consumer surface — `/search`, the profile resolver, `/go`, the Notify-Me fire — recomputed the predicate and listed them, while `runReVerification` and `findStalePractitioners` selected `where visible = true` and did not. The result was a listed Practitioner who was never re-verified again and whose staleness the operator could not see: ADR-0002's invariant ("every visible profile is currently verified") broken silently, by a cached copy of an answer nobody kept fresh.

**The crons now filter in TypeScript rather than in SQL, on purpose.** Both jobs select their candidates on what SQL can decide cheaply — for the stale alert, the `last_verified_at` threshold — and hand the rows to the same `isVisible()`/`hasMinFields()` pair the search filter uses. Expressing the predicate a second time in SQL would recreate the drift the column caused, one dialect further from the rule. The cost is a full scan of `practitioners` on two coarse maintenance jobs, and the `practitioners_visible_idx` partial index goes with the column; at Phase 1 scale that is not a trade worth optimising, and `search-impl.ts` already filters this way on the consumer path. If the table outgrows it, the fix is a generated column or an indexed view derived from the same rule — not a flag a writer must remember to update.

**"Hiding" a Practitioner therefore means changing the state the predicate reads.** The weekly cron's not-found branch writes `verification_status = 'revoked'` and nothing else; the revocation refund cancels the subscription; a lapsed card moves `subscription_status` through Stripe's dunning states. Each of those hides the profile as a consequence of the fact it records, which is the only way visibility can be both correct everywhere and impossible to forget.
