# Refund-on-revocation is idempotent via a record-first ledger and reuses the Resend mock gate

The refund-on-revocation handler (issue #17, fulfilling the prorated-refund promise in ADR-0004) is invoked synchronously from the weekly re-verification cron's `not-found` branch — there is no new event bus, consistent with ADR-0007. Idempotency is enforced by a new `public.revocation_refunds` ledger keyed on `practitioner_id`, mirroring the `public.stripe_events` table from the Stripe webhook slice: the handler's first write is an `insert ... on conflict do nothing returning practitioner_id`, and a replay short-circuits to a no-op before any Stripe call or email. This gives the spec's required "no double-cancellation, no duplicate emails" property.

We record **before** acting rather than after. The trade-off: if the Stripe cancel throws after the ledger row is written, a retry is a no-op and the refund is silently skipped. We accept this because the alternative (record-after-success) risks a double cancellation when a call succeeds Stripe-side but the process dies before recording — and the spec prioritises no-double-cancellation. The handler emits a structured `[revocation-refund]` log line so an operator can recover the rare stuck case manually.

A subscription already in a terminal state (`canceled`/`unpaid`) or with no `stripe_subscription_id` takes a no-Stripe path and an email that says the Practitioner was already not being billed. The Practitioner notification reuses the existing Resend-over-fetch sender (extracted to `src/server/resend.ts`) and is gated by the existing `ALERT_MOCK` flag rather than a new toggle — keeping the test suite and local runs offline, consistent with the project's `*_MOCK` idiom. No new npm dependency and no new environment variable are introduced.
