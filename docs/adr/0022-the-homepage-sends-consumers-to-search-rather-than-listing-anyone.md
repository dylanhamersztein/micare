# The homepage sends consumers to search rather than listing anyone

Until this slice `/` was the Slice 1 bootstrap: a heading, a count, and every visible **Practitioner** in a bare `<ul>`. It is now two doors on one page — a search entry point for consumers and a priced offer for **Practitioner** prospects — and it lists nobody.

**Dropping the listing is a product decision, not a tidy-up.** A directory that renders its whole membership on the front page is a directory that answers the wrong question: nobody arrives wanting to read every optician in the United Kingdom, they arrive wanting the ones near them, which is what `/search` is for and what the ranking rules in ADR-0018 are about. The listing also aged badly by construction — it grew unbounded, was ordered by name rather than distance, and put a paying **Practitioner**'s exposure on a page where position was decided by the alphabet. `getVisiblePractitioners` (`src/server/practitioners.ts`) existed only to feed it and was referenced by no test, so it went with the list rather than lingering as dead code; the homepage now has no loader and no server function at all, and renders the same for every visitor.

**The search controls are a second copy of `/search`'s, deliberately.** The two forms look identical and are not the same control: the homepage's hands the query to another route and then stops existing, while `/search`'s stays on screen with the searched-for terms still in it so a consumer widening a radius never retypes their postcode. Sharing them would mean a component parameterised by its own `data-testid`s — the E2E suite navigates the two by different markers — for the sake of about thirty lines of JSX over two primitives that are already shared. ADR-0018 drew this line once already, keeping the Notify-Me capture inside `search.tsx` rather than extracting it; the radii themselves do come from one place (`ALLOWED_RADII_MILES`), which is the part that could actually drift.

**The offer claims only what MiCare does.** The Practitioner block names £29 a month, states that the register check happens before a card is asked for, that the listing goes live when the required fields are filled, that the dashboard reports a **Click-through** count for the current **Billing Cycle**, and that a cancelling **Practitioner** stays visible to the end of the period they paid for. Each of those is something the system already does — signup's synchronous check (ADR-0002), the visibility rule (ADR-0004), the dashboard's one number (ADR-0020). Nothing on the page promises traffic, ranking or an audience, because MiCare cannot yet measure any of them. The price is typed out rather than read from Stripe: `STRIPE_PRICE_ID` names a price object, not an amount, and a homepage that fetched Stripe to render a heading would be trading a fixed string for a network call and a failure mode.

**The persistent header search is still not built, and this slice did not build it.** ADR-0021 pencilled it onto this issue, on the grounds that the design puts a search band in the header of every page *below* the homepage. The acceptance criteria for the homepage slice do not mention it, and it is a change to `SiteHeader` — every route, signed in and out, at both widths — rather than a change to `/`. It is left where Slice 19 left it: the mobile header's second row carries the link to `/search`, and the band belongs to whoever picks up the shell next.
