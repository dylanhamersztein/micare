# Signup files the prospect it could not read as a `pending` Practitioner

When the register cannot be read at signup — an ambiguous page or a technical failure, both collapsing to `pending` (ADR-0002) — the signup orchestrator now inserts the `practitioners` row itself: `verification_status = 'pending'`, `subscription_status = 'incomplete'`, no Stripe customer, and the signup-time `verifications` rows linked to it. Checkout keeps ownership of the `verified` path, and adopts that row if the same GOC number comes back through it.

**Without the row, `pending` was a status nothing could reach.** `checkout-impl` hardcoded `verification_status = 'verified'` on the only insert outside `db/seed.sql`, and refused to run at all unless verification returned `found-active`. So the one state machine transition that produces a `pending` Practitioner never produced anything: the prospect saw the pending panel and the flow ended. `runManualVerification` looks its subject up by `goc_number`, so ADR-0014's whole recovery route — and story 43 behind it — could only ever answer `no-such-practitioner`. CONTEXT.md described a state the application could not enter (issue #66).

**Filing the prospect, rather than deleting the route.** The alternative was to accept that `pending` is not a Practitioner state: drop the manual-verification route, drop `pending` from the schema's check constraint, and rewrite ADR-0014 to say so. That throws away the only answer MiCare has for a legitimate sign-up who hit a bad ten seconds — the register's silence would become indistinguishable from a rejection, which is exactly the confusion the pending panel's copy exists to prevent (story 19). The row is what makes the promise in that copy keepable: something for the operator to act on, and the prospect's email to act with.

**A `pending` row is inert, so creating one costs nothing.** Visibility is computed from `verification_status` and `subscription_status` on every read (ADR-0024), and `pending` + `incomplete` fails both gates — the prospect is not in search, has no profile, and is not billed. The weekly re-verification cron sweeps only visible Practitioners, so it does not pick them up either; `pending` stays exactly as terminal as ADR-0014 assumes, cleared by a human or not at all.

**Filing is idempotent, and never touches an account that already exists.** The prospect who presses "Try the check again" gets one row, not one per press: signup looks the GOC number up first and files only when nothing is there. An email that is already taken under a *different* GOC number is somebody else's account, so that attempt files nothing and links nothing to them — `practitioners.email` is unique, and guessing which of the two people it belongs to is not signup's decision to make. Either way the attempt itself lands in the append-only `verifications` trail, which is where the evidence lives.

**Checkout adopts the pending row instead of inserting beside it.** Once the register answers — because the operator re-ran the check, or because a later attempt got through — the prospect returns to signup, is verified, and continues to payment. The row it wrote at signup already holds their GOC number and email, both unique, so a second insert could only collide. `adoptPendingPractitioner` updates that row in place to `verified` with the Stripe identifiers, guarded on `verification_status = 'pending'` so it can never quietly resurrect a `rejected` or `revoked` one. It keeps its `id` and `short_id`, and with them the verifications already linked to it and the session `src/server/checkout.ts` mints by email.
