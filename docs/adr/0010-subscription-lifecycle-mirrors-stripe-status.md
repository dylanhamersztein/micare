# The subscription lifecycle mirrors Stripe's status, and cancel-at-period-end is Stripe's clock to keep

`subscription-sync` completes the ADR-0004 lifecycle (issue #14) by mapping the remaining Phase 1 events onto `practitioners.subscription_status`: `invoice.payment_failed` on a subscription invoice moves a Practitioner to `past_due`, `customer.subscription.updated` mirrors Stripe's own status verbatim, and `customer.subscription.deleted` writes `canceled`. MiCare holds no lifecycle rules of its own — Stripe is the system of record for whether a subscription is paid, in dunning, or over, and the mapper's only job is to project that status onto the column ADR-0004's visibility predicate reads. `past_due` staying visible is not a special case here; it falls out of `isVisible`, which already tolerates the dunning window.

Only the statuses MiCare models (`active`, `trialing`, `past_due`, `unpaid`, `canceled`) are mirrored. Stripe statuses with no MiCare meaning — `incomplete_expired`, `paused` — return `null` and leave the row untouched, so a Stripe-side concept we have not reasoned about can never force a Practitioner into a state the visibility rules never anticipated. The alternative (a catch-all that coerced unknown statuses to something safe) would hide Practitioners on a status change we had not designed for.

**Cancellation scheduled at period end needs no MiCare state at all.** When a Practitioner cancels at period end, Stripe keeps reporting the subscription as `active` and only fires `customer.subscription.deleted` once the period actually ends. Mirroring the status therefore keeps them listed for the period they paid for, and hides them at exactly the right moment, with no stored `cancel_at_period_end` flag, no `current_period_end` column, and no time-dependent branch inside `isVisible`. We considered persisting both fields so the dashboard could show a "cancels on <date>" banner, and rejected it for this slice: it would create a second source of truth for a date Stripe already owns, and make visibility depend on the current clock — a property that is unpleasant to test and to reason about during an incident. If the banner is wanted later, it should read the date from Stripe rather than from a column we have to keep in sync.

Idempotency is unchanged from the Slice 7 design: the `public.stripe_events` ledger short-circuits a replayed event id before any state change, and the mapper's output is a plain `UPDATE ... where stripe_customer_id = $1`, which is naturally idempotent even if a replay slipped past. `unpaid` and `canceled` only ever change the status column — no profile field is cleared and no row is deleted — so a Practitioner who resubscribes gets their original listing back rather than rebuilding it.
