# The shell reads the session at the root route

Every page now renders inside a header and a footer supplied by the root route, and that header has to know whether it is talking to a signed-in Practitioner before it can choose between "Sign in" and "Dashboard". `readSession()` is server-side and was called from exactly one place — `/dashboard`'s own loader, through `loadDashboard`. Serving the header means the root route reads the session too, which gives every page in the app a session read.

**That is a change in shape, not a detail, so it is written down here.** Before this slice a request for a public profile touched no session at all; now it reads and unseals the `micare_session` cookie on the way past. The cost is one HMAC verification per request against a cookie the browser was already sending — no database round-trip, no Supabase call, nothing that scales with the number of Practitioners. What it buys is a shell that can answer "who is looking at this?" on every page rather than on one, which is the precondition for the header, and later for anything else that has to differ for a signed-in Practitioner. The alternative — leaving the read where it was and having the header guess, or fetching it from the client after paint — trades a cheap server read for a flash of the wrong header.

**Only the answer crosses the wire.** `readShellSession` (`src/server/shell-session.ts`) returns `{ signedIn: boolean }` and nothing else. The session holds `practitionerId` and `email`; the shell needs neither, so neither is serialised into the page. A component that wants to know *who* the Practitioner is still asks a loader that has a reason to know — `loadDashboard` is unchanged, and still does its own `readSession()`, because it needs the email to load the read model and needs to redirect when there is no session at all.

**A root loader does not re-run on a client navigation, so sign-out has to say so.** `/dashboard`'s sign-out clears the cookie server-side and then navigates to `/login` in the client. Without an explicit `router.invalidate()` between the two, the root loader's cached `{ signedIn: true }` survives the navigation and the Practitioner lands on the sign-in page still being offered a dashboard they no longer have. Signing *in* needs no equivalent: the magic link is consumed by a server handler at `/auth/callback` that responds with a redirect, so the browser does a full load and the root loader runs again on its own. `tests/unit/shell.test.ts` holds the invalidation in place.

**The devtools panel is removed by the build, and that is why it is not wrapped in a condition.** `@tanstack/devtools-vite` — already registered in `vite.config.ts` — deletes the `<TanStackDevtools>` element and its imports from a production build; the built client bundle contains no TanStack devtools code at all. Guarding the element with `import.meta.env.DEV` does not help and actively breaks: the plugin removes the element and leaves the empty conditional behind, and the router's code splitter then fails to parse the file. The guard is the plugin. The unit suite asserts the plugin is registered and explains, where the next person will look, why the element is bare.

**The shell links only where there is somewhere to go.** The design's header and footer name several destinations Phase 1 does not have — "How Verification works", "Report a listing", About, Accessibility, Contact, Help for Practitioners. A link to a 404 is worse than an absent link, so the shell carries the four routes that exist: search, signup, sign-in and the dashboard. The privacy policy and terms have a slot rather than a link: `SiteFooter` takes a `legalLinks` prop that is empty today and renders no legal column while it is empty, so #46 lands as a list of two entries and not as a layout change. Those two arrive as plain `href`s rather than typed routes, because a route that does not exist cannot be typechecked against the router.

**There is no hamburger, and the mobile header wraps instead.** Three consumer destinations, one of which is the page you are already on, do not earn a gesture, a tap and a 24px icon in front of someone whose eyesight brought them here. The bar wraps to two rows on a narrow screen: identity and account on the first, the route to search on the second. The design puts a persistent search control in that second row on every page below the homepage; that control is the homepage slice's (#45) to build, and until it exists the second row carries the link to `/search` so a consumer on a phone still has a way there. "List your Practice" stays in the header at both widths — the acceptance criteria ask for a header route to signup, and the footer's full-size offer is a second way there rather than the only one.
