# Re-verification runs on Vercel Cron; stale-verification alerts go to the operator by email and log

The weekly re-verification job and the daily stale-verification alert are scheduled by **Vercel Cron**, declared in `vercel.json` under `crons` — `re-verify` weekly (`0 3 * * 1`, Mondays 03:00 UTC) and `stale-alert` daily (`0 8 * * *`, 08:00 UTC). Each schedule hits a route under `src/routes/api/cron/` that is guarded by comparing the `Authorization: Bearer <token>` header Vercel attaches against `CRON_SECRET`, so the endpoints can't be triggered publicly. Vercel Cron was chosen over an in-process scheduler (`node-cron`) or Supabase `pg_cron` because MiCare deploys to Vercel: scheduling lives in the repo next to the routes it invokes, needs no always-on process, and adds no new external dependency. The daily alert is delivered two ways — a single structured log line (durable, queryable in Vercel logs as the audit trail) **and** a digest email to `OPERATOR_ALERT_EMAIL` sent via the `RESEND_API_KEY` already wired into `env.server.ts`. Email sending follows the project's `*_MOCK` idiom: `ALERT_MOCK` (default `true`) short-circuits the send to a log line so the test suite and local runs stay offline, mirroring `AUTH_MOCK`/`GOC_MOCK`/`VITE_STRIPE_MOCK`. The stale threshold is configurable via `STALE_VERIFICATION_DAYS` (default `14`). The weekly job's `verified → revoked` transitions are *not* given a new event bus: the status flip plus the row written to `verifications` (subject to the existing 24h suppression cache) is itself the signal the separately-sliced refund-on-revocation handler consumes. Trade-off: Vercel Cron's minimum granularity and per-plan job limits cap how finely these can be scheduled, and the cron endpoints are protected by a shared secret rather than network isolation — both acceptable for two coarse, idempotent maintenance jobs.
