# RLS is a deny-all perimeter, enabled from migrations, and never the authorization mechanism

Every table in `public` has row level security enabled by `0008_enable_rls.sql` and carries no policies. A table with RLS on and zero policies denies every row to every non-superuser, non-owner role, so `anon` and `authenticated` — the two roles PostgREST hands to anything holding an anon key — can read and write nothing. That is the whole intent: the perimeter is closed, not configured.

**MiCare does not authorize through RLS, and adding policies would not change that.** ADR-0006 put the entire data layer on one path: the service-role `pg` pool in `src/server/db.ts`. The service role bypasses RLS, so every authorization decision MiCare makes — which Practitioner a session may edit, which rows a cron sweeps, which profile is visible — is re-derived in server code from the `pg` row on each request, exactly as before this migration. The perimeter exists for the case where a request reaches Postgres *without* passing through that code: a leaked anon key, a PostgREST endpoint left exposed, a Supabase client instantiated in the browser by a future slice. It is a second wall behind the application, not a mechanism the application leans on.

**Encoded in migrations because the hosted default is not a guarantee.** The four tables deployed to the hosted project (`practitioners`, `verifications`, `clickthroughs`, `notify_subscriptions`) already had RLS enabled before this slice, with no migration having asked for it. The source is `public.rls_auto_enable()`, a Supabase-installed event trigger that fires on `CREATE TABLE` in `public`. It is a platform artifact: absent from this repository, referenced by no migration, and asserted by no test. Any environment built from these migrations without it — a Supabase branch, a self-hosted instance, a new project, and in particular the local Compose stack that CI runs against, where all eight tables reported `relrowsecurity = false` — came up with the perimeter wide open and nothing noticed. The repository must not depend on `rls_auto_enable()` to provide RLS; it now provides its own. `enable row level security` is idempotent, so the migration is a no-op against the tables the trigger already covered.

**The guard is a test, not a convention.** `tests/integration/rls.test.ts` asserts that no table in `public` has RLS off and that no policy exists on any of them. A table added by a later migration without its own `enable row level security` fails CI, which is the only durable way to keep a per-table list honest; a comment asking future migrations to remember would not survive. The second assertion is deliberate too — if a slice ever needs a permissive policy, it should have to delete a line from this test and revisit this ADR, rather than quietly opening a hole in a perimeter everything else assumes is sealed.
